## 1. What features exist today (backend endpoints, frontend pages, admin features, analytics, roles)?

### Takeaway
Vitabot is a monolithic FastAPI app (`main.py`, about 70 routes, plus 7 routers) with an Angular frontend. It provides:
- multi-tenant RAG chat (pgvector, bilingual EN/AR) with media, slides, TTS and STT;
- FAQ and error-solution management;
- support tickets as a human handoff;
- tenant-admin analytics;
- superadmin AI monitoring;
- an embeddable widget with JWT SSO;
- Odoo SSO;
- a read-only Odoo "Ask Odoo" agent that uses Claude tool calling.

Three Odoo addons exist: `cpbot_vita_bot_link`, `cpbot_vita_insights` and `cpbot_rag_assistant`, all for Odoo 15.

**Backend core and chat**

- DB access goes through `db.tenant_connection(tenant_id)`, which sets the Postgres GUC `app.current_tenant` inside a transaction (an RLS hook). The pool comes from `DATABASE_URL` — [db.py:8-24](db.py)

  - applies the `[[NO_INFO]]` / no-info fallback, which sets `offer_support=True`;
  - persists user and assistant messages;

## 2. How does "Ask Odoo" work? Does it read via XML-RPC/JSON-RPC, with which credentials? Any writes? Any LLM tool calling?

### Takeaway
Ask Odoo is a **Claude tool-use agent**: `claude-sonnet-5`, at most 4 rounds and 19 tools, all read-only plus a `present_chart` UI tool. It calls Odoo over **XML-RPC** using a **single service account per Odoo instance**: either env `ODOO_USERNAME`/`ODOO_PASSWORD` for Vita Care's own Odoo, or an encrypted per-client row in `odoo_client_connections` looked up by `client_key`. It never acts as the end user. The end user's identity is only an email string placed in the system prompt. **No write calls exist anywhere in the codebase.** The prompt explicitly forbids suggesting that permissions can be changed.

### Cited Findings

**Transport and credentials**
- `OdooClient` wraps url, db, username and password and caches the uid. It authenticates with `xmlrpc.client.ServerProxy(f"{url}/xmlrpc/2/common").authenticate(...)` and calls `models.execute_kw(db, uid, password, model, method, args, kwargs)` — [services/odoo_service.py:31-80](services/odoo_service.py)
- `_execute_kw` is generic (any model and method), so it could technically call `write`/`create`. Today every caller uses only `search_read`, `read` and `search_count` — [services/odoo_service.py:72-80, 82-528](services/odoo_service.py)
- The default client is built from env `ODOO_URL`, `ODOO_DB`, `ODOO_USERNAME` and `ODOO_PASSWORD` — [services/odoo_service.py:10-13, 532-536](services/odoo_service.py); [.env.example](.env.example)
- The per-client connection is `SELECT odoo_url, odoo_db, odoo_username, odoo_password_encrypted FROM odoo_client_connections WHERE client_key=$1`, with the password decrypted via `services/crypto.decrypt_value` (env `CLIENT_CREDENTIALS_ENCRYPTION_KEY`) — [services/odoo_service.py:539-568](services/odoo_service.py); [services/crypto.py](services/crypto.py); [.env.example](.env.example)
- Routing: `/odoo/ask` loads the caller's `users.odoo_client_key`. If one is set, the request goes to that client's Odoo; otherwise it goes to Vita Care's default Odoo — [main.py:3034-3041](main.py)

**Agent loop**
- `odoo_agent_ask()`:
  - prefetches a "VERIFIED CURRENT SALES SUMMARY";
  - adds a `CURRENT USER IDENTITY` block (email and display name) and the top-3 KB chunks as "RELEVANT COMPANY MANUAL EXCERPTS";
  - loops `anthropic_client.messages.create(model=SONNET_MODEL, max_tokens=2500, system=..., tools=TOOLS, messages=...)` for up to `max_tool_rounds=4`;
  - executes each `tool_use` block through a per-request `partial(fn, client=odoo_client)`;
  - appends the `tool_result`s and returns `{"answer","chart"}`.
  — [services/odoo_agent.py:419-575](services/odoo_agent.py)
- Tools (input schemas at [services/odoo_agent.py:159-394](services/odoo_agent.py), dispatch table at 396-416): search_orders, search_invoices, search_customers, get_customer_orders_summary, get_top_products, get_top_customers, get_stock_levels, search_products, get_installed_apps, get_available_apps, get_system_users, get_company_info, get_currencies, get_warehouses (described as "warehouses/branches"), get_sales_teams, get_product_categories, get_payment_methods, get_user_access_rights, get_area_admins, present_chart.
- The prompt is explicitly read-only on permissions: "This tool is strictly read-only… Never suggest or imply that permissions can be changed through this assistant, and never attempt to call any modification" — [services/odoo_agent.py:90-99](services/odoo_agent.py). The tool description says "read-only — this only reports what access a user currently has, it never changes anything" — [services/odoo_agent.py:341-347](services/odoo_agent.py)
- "Can I do X" questions are answered by the LLM reading group names returned by `get_user_access_rights`. This is heuristic reasoning, not an Odoo ACL check (`check_access_rights`) — [services/odoo_agent.py:113-121](services/odoo_agent.py)

**Access-rights lookups**
- `get_user_access_rights(name)` does `res.users search_read` with the domain `['|', ('name','ilike',name), ('login','ilike',name)]`, `limit: 1`. It then reads `res.groups` `full_name`/`category_id` and filters out the categories Administration, Technical and Extra Rights. On a miss it returns **all system usernames** to the LLM — [services/odoo_service.py:20, 431-471](services/odoo_service.py)
- `get_area_admins(user_email)` matches `login = user_email` exactly. For each non-sensitive category it finds groups named "Administrator" and returns up to 5 admins plus a count — [services/odoo_service.py:473-528](services/odoo_service.py)
- Group membership is read from the Odoo 15 field name `groups_id` — [services/odoo_service.py:435, 477](services/odoo_service.py)

**History, persistence and limits**
- `/odoo/ask` takes `history: list[dict]` from the **request body**, supplied by the client. It is not loaded from the DB, and the Odoo Q&A is not persisted to `messages`/`conversations`. There is no `@limiter.limit` decorator on `/odoo/ask` — [main.py:3012-3051](main.py)
- Only per-call latency and status go to `ai_predictions_log` (endpoint='odoo_agent') — [services/odoo_agent.py:517-528](services/odoo_agent.py)
- Blocking calls: `odoo_agent_ask` is a synchronous function (blocking XML-RPC plus the sync Anthropic SDK) called directly inside `async def odoo_ask`. There is no `to_thread` or executor (a grep found none in main.py, routers/ or services/) — [main.py:3042](main.py); [services/odoo_agent.py:419](services/odoo_agent.py)
- `/odoo/dashboard` always queries the default Vita Care Odoo, ignoring `client_key` — [main.py:3001-3010](main.py)

**Other Ask Odoo entry points**
- The `cpbot_vita_insights` Odoo addon calls `/odoo/ask` with a long-lived Bearer token copied into Odoo settings — [cpbot_vita_insights/static/src/js/cpbot_chat_widget.js:50-66, 116-123](cpbot_vita_insights/static/src/js/cpbot_chat_widget.js)
- `generate_odoo_token.py` mints such tokens: an HS256 JWT with a hardcoded `user_id`/`tenant_id`, `"role": "admin"`, valid 365 days — [generate_odoo_token.py:1-13](generate_odoo_token.py)
- There is also an `odoo_test.py` script at the repo root ([odoo_test.py](odoo_test.py)), not reviewed.

### Inferences
- The tool-calling scaffold (`TOOLS` list, `_TOOL_FUNCTIONS` map, multi-round loop, structured side-channel output such as `chart_payload`) is exactly the pattern a write-action layer needs. A `propose_*` tool could return a pending-action payload the same way `present_chart` returns a chart.
- The bot does all Odoo work as a single privileged service account, so Odoo's own record rules and ACLs are evaluated for that account, not for the requester. Any write feature must add **explicit requester-authorization** on top. Otherwise any vitabot member routed to that Odoo could get the service account to make changes.
- `get_user_access_rights` uses an ilike match with limit 1, which can resolve to the wrong person on partial or ambiguous names. That is acceptable for read-only Q&A but unsafe as a basis for authorizing writes. Writes should key on `odoo_user_id`, not fuzzy name or email.
- Because history is client-supplied, a caller can fabricate prior assistant turns or "confirmations". A write-confirmation flow must not trust chat history and must use a server-side pending-action record.

### Gaps
- Which Odoo account each `odoo_client_connections` row uses (admin, or a limited integration user), and its group memberships, is data in the production DB and not visible in code.
- Whether the `/odoo/ask` endpoint is actively used in production (the frontend route is disabled; the superadmin page and the Odoo addon remain) could not be determined from code.

## 3. How does the Odoo SSO identify the user, and which Odoo version is targeted? Are Odoo groups or rights carried into the bot?

### Takeaway
The addon (Odoo **15**, version `15.0.1.0.9`) sends a signed payload: `email=user.login`, `username=user.name`, `odoo_user_id=user.id`, the instance's `client_key` and a `company_slug` taken from the subdomain. The payload is HMAC-SHA256 signed with a per-client secret and replay-bounded to 300 s. The backend provisions a vitabot **`member`** keyed by `odoo_identity = "{client_key|internal}:{odoo_user_id}"`. **No Odoo groups, no Odoo company_id or allowed company_ids, and no access rights** are transmitted or stored. The resulting JWT does not even carry `company_id` or the Odoo user id. It is valid for **10 years** by default.

### Cited Findings

**What the addon sends**
- The manifest version is `'15.0.1.0.9'` (bumped from 15.0.1.0.8 in the uncommitted diff). It depends on `base` and `web` — [cpbot_vita_bot_link/__manifest__.py:3, 46](cpbot_vita_bot_link/__manifest__.py)
- The controller route is `/vita_bot/sso` (`auth="user"`, `csrf=False`). It rejects portal users (`user.share`), then reads `email = user.login`, `username = user.name`, `odoo_user_id = user.id` — [cpbot_vita_bot_link/controllers/sso.py:219-250](cpbot_vita_bot_link/controllers/sso.py)
- The client key, SSO secret, backend URL, frontend URL and company domain are read from `ir.config_parameter` (Settings > General Settings > Vita Bot) — [cpbot_vita_bot_link/controllers/sso.py:252-278](cpbot_vita_bot_link/controllers/sso.py); [cpbot_vita_bot_link/models/res_config_settings.py:7-63](cpbot_vita_bot_link/models/res_config_settings.py)
- The signature covers `client_key\nodoo_user_id\nemail.lower()\nusername\ncompany_slug\ntimestamp`, HMAC-SHA256. It is sent in the headers `X-Odoo-Sso-Timestamp` and `X-Odoo-Sso-Signature`, with `allow_redirects=False` — [cpbot_vita_bot_link/controllers/sso.py:150-155, 280-302](cpbot_vita_bot_link/controllers/sso.py)
- JSON body fields sent: `email`, `username`, `odoo_user_id`, `client_key`, `company_slug`. Nothing about groups or companies — [cpbot_vita_bot_link/controllers/sso.py:286-292](cpbot_vita_bot_link/controllers/sso.py)
- The company slug comes from the request Host, falling back to `web.base.url` (uncommitted change), e.g. test-life.vitacareonline.com gives "test-life" — [cpbot_vita_bot_link/controllers/sso.py:158-191](cpbot_vita_bot_link/controllers/sso.py)
- The browser is redirected to `{frontend}/sso-login?code=…`. That is a single-use exchange code, not the token — [cpbot_vita_bot_link/controllers/sso.py:346-347](cpbot_vita_bot_link/controllers/sso.py)

**The already-known Referer issue**
- `_back_to_odoo_url()` returns the `Referer` if its netloc equals the request's own `host_url` netloc, else `/web`. The docstring concedes the value is attacker-controlled, and every call site HTML-escapes it — [cpbot_vita_bot_link/controllers/sso.py:194-214, 245, 277, 328](cpbot_vita_bot_link/controllers/sso.py)
- The same-host comparison relies on `request.httprequest.host_url`, which itself derives from the Host header.

**Backend verification and provisioning**
- The request model is `OdooSSORequest`: email, username, client_key, odoo_user_id, company_slug — [main.py:583-590](main.py)
- `_verify_odoo_sso_signature` enforces 300 s timestamp freshness and constant-time comparison against both the current canonical string and a legacy one without the slug — [main.py:609, 617-657](main.py)
- Hardened path:
  - the secret comes from `odoo_client_connections.sso_secret_encrypted` for that `client_key`, or from env `ODOO_SSO_INTERNAL_SECRET` when there is no key;
  - the tenant is always `VITA_CARE_TENANT_ID`;
  - `odoo_identity = f"{client_key or 'internal'}:{odoo_user_id}"`;
  - the user is matched by `odoo_identity`, then by email (now also claiming rows whose `company_id IS NULL`, an uncommitted change);
  - otherwise a new user is inserted with **`role 'member'`** and a random password.
  — [main.py:674-784](main.py); [services/odoo_service.py:571-585](services/odoo_service.py)
- Token claims issued on SSO: `user_id`, `tenant_id`, `role`, `username`, `email`, `tv`, with `expire_minutes=ODOO_SSO_TOKEN_EXPIRE_MINUTES`. **There is no `company_id`, no odoo_user_id and no groups** — [main.py:786-796](main.py)
- `/login` by contrast includes `company_id` — [main.py:559-567](main.py)
- `ODOO_SSO_TOKEN_EXPIRE_MINUTES` defaults to `10*365*24*60`, i.e. 10 years — [main.py:597](main.py)
- The code is stored in `sso_exchange_codes` with a 60 s TTL and single use, and exchanged at `/auth/odoo-sso/exchange` (rate limited 20/min) — [main.py:614, 803-810, 906-923](main.py)
- A legacy path still accepts a single shared `X-Odoo-Sso-Secret` (env `ODOO_SSO_SECRET`), matches users by email only, and returns the raw `access_token` in the JSON body — [main.py:816-899](main.py)
- Server-side logout works by bumping `users.token_version`. Tokens without a `tv` claim are accepted until they expire — [core/auth.py:35-67](core/auth.py); [main.py:943-971](main.py)

### Inferences
- The only persistent link from a vitabot user to their Odoo identity is `users.odoo_identity` ("clientkey:uid") plus `users.odoo_client_key`. A write-action layer can recover the requester's **Odoo uid** from `odoo_identity` (split on ':') without changing the SSO protocol. This is more reliable than the email match Ask Odoo uses today ([services/odoo_agent.py:461-474](services/odoo_agent.py)).
- Because no Odoo groups are carried, vitabot cannot know at SSO time whether the user is an Odoo "Administration / Access Rights" or "Settings" user. Permission must be checked **live in Odoo** at action time, which is better anyway since rights change. Two options:
  - read `res.users` `groups_id` for that uid via the service account and check for e.g. `base.group_erp_manager` (Access Rights) or `base.group_system` (Settings), using `res.users.has_group` semantics;
  - better, execute the write inside Odoo as that user so Odoo's own ACLs apply.
- The 10-year SSO token is a risk to weigh before enabling writes. A stolen SSO-derived token would allow write actions for years unless `token_version` is bumped. Write actions should require a fresh, short-lived session or a step-up re-SSO.
- The JWT lacking `company_id` on the SSO path means `get_current_company_id` returns None for SSO users ([core/auth.py:145-153](core/auth.py)). If an SSO user is promoted to `company_admin`, `require_admin_or_company_admin` would 403 them with "No company assigned" ([core/auth.py:174-180](core/auth.py)). This was not tested; it is an inference from the code.

### Gaps
- Odoo 15's exact group XML IDs present on each client's instance (e.g. whether "Multi Companies" `base.group_multi_company` is enabled) is per-instance data, not in this repo.
- Whether all client Odoo instances run the hardened addon version, rather than the legacy shared-secret one, is not determinable from code.

## 4. What roles and permission model exist inside vitabot itself?

### Takeaway
There are four effective roles carried in the JWT: `superadmin`, `admin` (tenant admin), `company_admin` (scoped to one `company_id`) and `member`. They are enforced by FastAPI dependencies in `core/auth.py`. A superadmin can act as any tenant through the `X-Acting-Tenant` header. Enforcement is inconsistent: several write endpoints check only tenant membership, not role.

### Cited Findings

**Dependencies**
- `get_current_tenant` returns the `x_acting_tenant` header value when `role == "superadmin"` — [core/auth.py:99-111](core/auth.py)
- `require_superadmin`, `require_admin` (admin or superadmin), `require_admin_or_company_admin` (returns a `UserScope`; callers must enforce the company scope themselves), `require_vita_care_tenant`, `require_vita_care_admin` and `require_housing_bank_tenant` — [core/auth.py:123-228](core/auth.py)
- Roles an admin may assign: `{"admin","company_admin","member"}`. Company admins are restricted to their own company in user CRUD — [main.py:188, 232, 249-358](main.py)

**Endpoints with no server-side role check** (only `get_current_tenant`, and no role comparison in the handler body; a grep of main.py for role comparisons found checks only at lines 188-358, 2152 and 2223):
- `POST/PUT/DELETE /faq` — [main.py:2786-2840](main.py)
- `POST /users/import/preview` and `POST /users/import/confirm`. Confirm accepts roles `{"admin","editor","member","auditor"}` and sets the default password `"Welcom123!"`. Any authenticated member could bulk-create admins — [main.py:2536-2660, 2614-2618](main.py)
- `POST /media/link` — [main.py:2576-2585](main.py)
- Excel row create/update/delete — [main.py:1536-1624](main.py)
- `POST/DELETE /odoo/suggested-questions` (any Vita Care member) — [main.py:3069-3100](main.py)
- FAQ category admin routes under `/admin/faq-categories` use `get_current_tenant` only — [routers/faq_categories.py:26-95](routers/faq_categories.py)

**Inconsistencies and frontend**
- The roles `editor` and `auditor` appear only in user import and LLM mapping, not in auth dependencies — [main.py:2617](main.py); [services/import_users.py:48](services/import_users.py)
- Frontend guards: admin, auth, company-admin, guest, housing-bank-tenant, member, shared-page, superadmin, upload-lock, vita-care-tenant — [frontend/src/app/core/guards/](frontend/src/app/core/guards/)

### Inferences
- There is no notion of "may perform Odoo administrative actions" in vitabot's role model. A write feature needs either a new vitabot permission (e.g. a per-tenant `odoo_actions_enabled` flag plus per-user capability), or it should defer entirely to the requester's Odoo groups (see §3).
- Fixing the missing `require_admin` on the endpoints above is a cheap, high-value hardening item, separate from the write-action feature.

### Gaps
- DB-level RLS policies could not be verified because the migrations are gitignored and absent. `PRODUCT_AUDIT.md` claims the policies exist but are bypassed because the app connects as `postgres`/`rds_superuser` ([PRODUCT_AUDIT.md:11, 39](PRODUCT_AUDIT.md)). Treat that as unverified: the production DB role is not visible.

## 6. Where would a write-action / tool-calling layer most naturally plug in, and what pieces would need to be added?

### Takeaway
The natural plug point is the existing Claude tool loop in `services/odoo_agent.py`, the `OdooClient._execute_kw` transport, and the `/odoo/ask` endpoint. Today there is no requester Odoo uid in the request context, no permission check against Odoo groups, no pending-action/confirmation mechanism, no audit table, and execution runs only as a shared service account. All of these must be added. A user-branch change in Odoo 15 maps to writing `res.users.company_ids` (allowed companies) and possibly `company_id` (default company) with x2many commands.

### Cited Findings
- Tool registry and dispatch: the `TOOLS` schema list ([services/odoo_agent.py:159-394](services/odoo_agent.py)) and the `_TOOL_FUNCTIONS` map ([services/odoo_agent.py:396-416](services/odoo_agent.py)). Per-request binding is `partial(fn, client=odoo_client)` ([services/odoo_agent.py:505](services/odoo_agent.py)). Special-cased UI tools like `present_chart` capture args into a side payload instead of calling Odoo ([services/odoo_agent.py:543-551](services/odoo_agent.py)).
- The return shape `{"answer", "chart"}` is passed straight through by `/odoo/ask` ([services/odoo_agent.py:536](services/odoo_agent.py); [main.py:3051](main.py)), so an extra `pending_action` key would be a natural extension.
- Transport: `OdooClient._execute_kw(model, method, args, kwargs)` can already issue `write` over XML-RPC, but it authenticates as the configured service account ([services/odoo_service.py:47-80](services/odoo_service.py)).
- Requester context available at `/odoo/ask` today: vitabot `user_id`, `tenant_id`, email, username and `odoo_client_key` — [main.py:3022-3031](main.py). The Odoo uid is not loaded, but is stored in `users.odoo_identity` as `"{client_key|internal}:{odoo_user_id}"` — [main.py:695, 727, 759-763](main.py)
- Existing read-side building blocks for permission checks: `res.users` `groups_id` and `res.groups` reads — [services/odoo_service.py:431-471](services/odoo_service.py). The warehouses tool is already described to the LLM as "warehouses/branches" — [services/odoo_agent.py:316-321](services/odoo_agent.py)
- The Odoo addon already has a trusted, HMAC-signed channel per instance: a per-client secret in `ir.config_parameter`, with the matching `odoo_client_connections.sso_secret_encrypted` on the backend — [cpbot_vita_bot_link/controllers/sso.py:150-155, 274](cpbot_vita_bot_link/controllers/sso.py); [services/odoo_service.py:571-585](services/odoo_service.py). Today it only goes addon to backend.
- The frontend already has a shared confirm dialog component and service usable for a confirmation card — [frontend/src/app/shared/confirm-dialog/](frontend/src/app/shared/confirm-dialog/); [frontend/src/app/core/services/confirm-dialog.service.ts](frontend/src/app/core/services/confirm-dialog.service.ts)
- The "support ticket" pattern (a server-side record with state and an admin resolve step) is an existing model for an approval workflow — [routers/support_tickets.py:27-321](routers/support_tickets.py)
- The system prompt currently prohibits any modification talk, so it would need revising — [services/odoo_agent.py:95-99](services/odoo_agent.py)

### Inferences
These are design implications; they still need validating against Odoo 15 documentation, which is outside this codebase audit.

1. **Resolve the requester's Odoo uid server-side.** In `/odoo/ask`, select `odoo_identity`, parse the uid, and pass it to `odoo_agent_ask` (new param `requester_odoo_uid`). Never take it from the LLM or the request body. Optionally add `odoo_uid` to the SSO JWT claims at [main.py:786-796](main.py).
2. **Add `propose_*` tools, not direct write tools.** Examples: `propose_set_user_companies(target_user, add_company_ids, remove_company_ids)`, `propose_set_user_active`, and later `propose_add_user_group`. They resolve the target by exact id after disambiguation, not by ilike plus limit 1 ([services/odoo_service.py:432-436](services/odoo_service.py)). They return a preview, i.e. the current `company_ids` against the proposed ones, plus a server-generated `action_id`. They are captured like `present_chart` and never executed in the LLM loop.
3. **Add a pending-action table**, e.g. `odoo_pending_actions(id, tenant_id, requester_user_id, requester_odoo_uid, client_key, model, record_id, operation jsonb, preview jsonb, status, expires_at, created_at, decided_at, executed_at, result jsonb, error)`. Add an endpoint `POST /odoo/actions/{id}/confirm` (and `/cancel`) that re-checks ownership, expiry and status, then executes. This also neutralizes the client-supplied-history problem ([main.py:3012-3014](main.py)).
4. **Re-check permission at confirm time, live in Odoo.** Two options:
   - (a) Service-account execution plus an explicit check that the requester uid holds the required group (e.g. Administration / Access Rights, `base.group_erp_manager`) and that every target company is within the requester's own allowed `company_ids`. Both are read via the existing `_execute_kw` reads.
   - (b) Preferred for least privilege: a new signed endpoint in the `cpbot_vita_bot_link` addon (e.g. `/vita_bot/action`, HMAC-verified with the same per-client secret). It runs the write as `request.env(user=requester_uid)` so Odoo's own ACLs and record rules decide. The service account then needs no write rights.
   - Option (b) requires extending the addon, which is already versioned and released per client ([cpbot_vita_bot_link/__manifest__.py:3](cpbot_vita_bot_link/__manifest__.py)).
5. **Odoo 15 data model for "allow/disallow user X on branch Y".** `res.users.company_ids` is many2many (allowed companies) and `company_id` is the default company. Use write commands `(4, id)` to add and `(3, id)` to remove. Removing the user's current default `company_id` must be blocked or handled. "Branch" is ambiguous in this codebase: it could mean `res.company` or `stock.warehouse` ([services/odoo_agent.py:318](services/odoo_agent.py)). The feature should confirm which one the user means.
6. **Audit and notifications.** Add an `odoo_action_audit` record, or reuse the pending-action row as the immutable audit, capturing who, what, before, after, Odoo response and IP. Surface it in admin analytics and, optionally, as a ticket-style notification to area admins (`get_area_admins` exists at [services/odoo_service.py:473-528](services/odoo_service.py)). Also log through `log_ai_prediction` with a new endpoint label.
7. **Session hardening before enabling writes.** Shorten the SSO token TTL or require a fresh SSO for confirmation, given the 10-year default ([main.py:597](main.py)). Add `@limiter.limit` to `/odoo/ask` and the confirm endpoint. Keep a per-tenant kill switch (feature flag), since tenant gating today is hardcoded ([core/auth.py:185-205](core/auth.py)).
8. **Frontend.** Re-enable or replace the disabled `vita-insights` route ([frontend/src/app/app.routes.ts:218-227](frontend/src/app/app.routes.ts)) or extend superadmin `odoo-chat`. Render a confirmation card from `pending_action`. The Odoo-embedded `cpbot_vita_insights` widget uses a static shared admin token ([cpbot_vita_insights/static/src/js/cpbot_chat_widget.js:50-66](cpbot_vita_insights/static/src/js/cpbot_chat_widget.js); [generate_odoo_token.py](generate_odoo_token.py)), so it should **not** get write actions without per-user identity.
9. **Tests.** Add unit tests for permission denial, a cross-company target outside the requester's companies, expired or replayed confirmation, and an LLM-fabricated `action_id`. Follow the existing pytest style in [tests/test_widget_sso.py](tests/test_widget_sso.py) and [tests/test_ask_conversation_ownership.py](tests/test_ask_conversation_ownership.py).

### Gaps
- Odoo 15 API specifics need confirming from Odoo docs or source (another researcher's scope): exact group XML IDs for "Access Rights", `has_group` availability over XML-RPC, constraints on `company_ids`/`company_id`, and multi-company record rules on `res.users`.
- Whether the per-client service accounts have rights to write `res.users` is unknown, because it is production data.
- Whether Vita Care wants admins in client companies (external Odoo instances) to perform such actions, or only Vita Care internal staff, is a product decision not encoded anywhere.
